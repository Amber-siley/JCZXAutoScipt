# 让 Agent 辅助用户生成任务（create-task-from-record 重设计）— Design

## 背景与问题

上一版（2026-08-28）设计让 agent 一站式「看屏 → 取点 → 裁模板 → 写配置 → 注册 → 验证」，模板由 agent 用 `save_template` 自裁。实机验证/用户反馈后，定位调整为：

- **agent 只辅助用户生成 task**，不替用户做全流程。
- **模板由用户提供，agent 只用不裁**（agent 不能自己生成模板）。
- **复杂场景需要门禁校验管控**（先确认条件再生成）。
- **多轮与用户对话**，用 tui-config 语法生成任务文件。
- skill 重点转为**详细分析用户提供的 record，尽量理解游戏画面与元素**。

## 目标（用户确认）

重设计 `create-task-from-record` skill 的作业流程：

| 维度 | 新定位 |
|------|--------|
| skill 角色 | 只辅助用户生成 task，不替用户做全流程 |
| 输入 | 用户提供的 record（JSON + 标注截图），做详细分析，尽量理解游戏画面与元素 |
| 复杂场景 | 门禁校验：先列出场景要素与未知条件，用户确认/补充后才生成 |
| 对话 | 多轮与用户对话，用 tui-config 语法生成任务文件 |
| 模板 | 由用户提供，agent 只用不裁（不自己生成模板） |
| MCP 工具 | `write_config` + `register_file` 保留常用；`save_template` 保留但限制（仅用户明确要求才用）；**新增 `list_templates` 校验工具** |

## 整体流程

```
用户提供 record + 标注截图
   │
   ▼
【阶段1 分析】读 record + 逐张看标注截图
   → 翻译每个动作为语义（点击了什么按钮/进入了什么界面）
   → 尽量理解游戏画面元素（这是什么界面、有哪些按钮、图标状态）
   │
   ▼
【阶段2 判定复杂度】
   简单：线性操作 → 可直接生成
   复杂：需条件判断/动态界面/依赖游戏状态 → 进门禁（硬门禁）
   │                          │
   │                          ▼
   │                  【门禁校验】
   │                  列出场景要素 + 未知条件
   │                  → 与用户逐一确认/补充
   │                  → 条件齐全才解锁生成
   ▼
【阶段3 多轮对话细化】与用户确认：
   - 操作目的/路径
   - 每个环节点哪、等什么
   - 条件分支（什么情况该这样/该那样）
   ▼
【阶段4 生成任务文件】
   用 tui-config 语法生成 task 文件
   → 模板引用用户已提供的（agent 不裁）
   → 先 list_templates 校验模板存在
   → write_config 写文件 + register_file 注册
   → reload_config 生效
   ▼
【阶段5 验证】run_entity / read_log_tail 与用户确认
```

## 阶段1：详细分析 record（尽量理解画面与元素）

- 读 `record_*.json`，按 `seq` 排序 actions，确认 `resolution`。
- **逐张看标注截图**，翻译每个动作为语义（"点击基地""点驻员预设""用预设2""返回"）。
- **理解游戏画面元素**：这是什么界面？有哪些按钮/元素？状态图标有哪些形态（绿✓/黄脸/红⊗）？
- 输出一版"操作语义清单"，复述给用户确认。

## 阶段2：判定复杂度

**复杂场景**（满足任一即进门禁）：
- 需要条件判断/分支（弹窗是否出现、图标是否某状态、预设是否已用）
- 依赖当前游戏状态（进入界面不固定、资源变化）
- 需要等待动态界面（加载、动画、轮换）
- 有二义性（同一操作可能产生不同结果）

简单场景（线性点击/滑动，无分支）：可直接生成。

## 门禁校验（复杂场景强制关卡）

**门禁是硬门禁**：场景要素不完整/条件未明，agent 不生成配置，只输出"还缺什么"。

**门禁动作**（需逐项与用户确认，全部确认后才写配置）：
1. **列出场景要素**：涉及哪些界面、哪些按钮、哪些状态图标。
2. **列出未知条件**：哪些行为依赖当前游戏状态、哪些情况需走不同分支。
3. **确认分支规则**：每个 condition 的"什么情况 → 走 which 分支"。
4. **确认兜底**：不确定当前在哪个界面时怎么处理（默认 `goto-home`）。

**门禁输出格式**（agent 必须产出这个清单再动手）：
```
## 场景要素
- 界面：主界面 → 基地 → 驻员状况
- 按钮/元素：驻员预设、返回、使用
- 状态图标：绿✓ / 黄脸 / 红⊗（心情）

## 未知条件
- Q1：预设2 若已在工作中，还要再点「使用」吗？
- Q2：若没看到「使用」按钮，是跳过还是等待？

## 分支规则
- 条件：红⊗ 出现 → 点「使用」；否则 → 返回

## 兜底
- 不确定在哪 → goto-home
```

**硬门禁**：若场景要素/分支规则/兜底任一项无法由用户补齐，不生成配置，只输出缺失项。

## 阶段4：生成任务文件 + 模板引用

**关键约束：agent 不自己生成/裁剪模板。**

- 模板由用户放在 `jczx/resources/record/<purpose>/`（用户自己裁好）。
- agent 写配置前，**先 `list_templates(purpose)` 校验模板存在**；缺失则列出并提示用户补充，不自己裁。
- `write_config` 写入任务时，`target` 用 `record\<purpose>\<name>.png`（仅引用确认存在的模板）。
- `register_file` 注册到 MainMenu；`reload_config` 生效。
- 多轮对话：逐步与用户确认生成内容，不一次性输出完整配置。

## MCP 工具调整

### 新增 `list_templates(purpose, pattern=None)`
- 列出 `resources/record/<purpose>/` 目录下的 `*.png` 模板文件。
- 支持**模糊匹配**：`pattern` 为可选入参，默认不传（列出全部）；传入如 `%staff_preset%` 则只返回文件名含该子串的模板。
- 返回文件列表（或空/不存在提示），让 agent 写配置前确认用户已提供哪些模板、缺哪些。

### 保留但限制 `save_template`
- 保留工具，但 **skill 默认不调用**（agent 不自主裁模板）。
- 仅在**用户明确要求**"帮我裁出这个按钮"时才调用。
- skill 写清楚：`save_template` 是用户显式请求才用的辅助工具，不是 agent 自主生成模板的默认路径。

### 保留常用 `write_config` / `register_file`
- agent 用它们写任务文件 + 注册，沿用上版实现。

## 排除范围
- 不新增坐标点击工具（`click_at`），仍用模板匹配。
- `save_template` 默认不用于 agent 自主裁模板。
- 真实 cv2 合成图匹配 / Textual TUI 测试：不涉及。
